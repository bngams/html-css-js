Projet 8 · Démonstration

📦 Quand un projet grossit

📖 Ceci n'est pas un exercice. Il n'y a rien à écrire, rien à rendre — une dizaine de minutes de lecture, pour reconnaître des lignes que vous croiserez bientôt.

L'objectif n'est pas de savoir les écrire aujourd'hui, mais de ne pas être perdu le jour où vous ouvrirez un projet existant.

1 · Le fil qui se termine ici

Depuis le projet 6, une question revient à chaque étape : comment charge-t-on du JavaScript ? Chaque réponse était motivée par une gêne réelle.

ProjetCommentLa gêne qui fait avancer
P6 la console du navigateur « rien n'est conservé »
P6 <script> dans la page « ça marche, mais ça pollue le HTML »
P7 un fichier app.js séparé « mieux — mais tout est dans un seul gros fichier »
P8 plusieurs fichiers, avec import c'est ce que nous regardons maintenant

2 · Le problème du fichier unique

Votre app.js de l'exercice 4 fait une cinquantaine de lignes. Imaginez-en deux mille : la classe Rectangle, le catalogue, les calculs, l'affichage, tout mélangé. Retrouver quelque chose devient pénible, et deux personnes ne peuvent plus y travailler en même temps.

La solution est la même qu'en CSS ou en HTML : découper. Un fichier par sujet.

3 · À quoi ça ressemble

Trois fichiers, au lieu d'un :

projet/
├── index.html
├── rectangle.js     ← la classe, et rien d'autre
├── catalogue.js     ← les données
└── app.js           ← le programme, qui utilise les deux

Le fichier qui offre quelque chose

rectangle.js

export class Rectangle {
  constructor(largeur, hauteur) {
    this.largeur = largeur;
    this.hauteur = hauteur;
  }

  calculAire() {
    return this.largeur * this.hauteur;
  }
}

C'est votre classe de l'exercice 4, à un mot près : export devant. Il signifie « ceci est disponible pour les autres fichiers ».

Le fichier qui demande

app.js

import { Rectangle } from "./rectangle.js";

const r = new Rectangle(10, 5);
console.log(r.calculAire());     → 50

import va chercher ce qu'un autre fichier a exporté. Le reste du code ne change pas d'un caractère.

Et dans le HTML

<script type="module" src="app.js"></script>

type="module" est indispensable. Sans lui, le navigateur refuse les import : 

SyntaxError: Cannot use import statement outside a module

C'est la seule ligne à changer dans le HTML — et app.js est le seul fichier à déclarer : les autres sont chargés automatiquement, parce qu'il les importe.

4 · Ce qu'il faut en retenir aujourd'hui

Vous voyez…Cela veut dire
export devant une classe ou une fonction « ce fichier la met à disposition »
import { X } from "./y.js" « ce fichier a besoin de X, qui vient de y.js »
<script type="module"> « ce projet est découpé en plusieurs fichiers »

Rien de plus pour aujourd'hui. Savoir les reconnaître vous évitera d'être perdu devant un projet existant. Savoir les écrire ne vous servira que le jour où vos fichiers deviendront trop gros — et ce jour-là, vous aurez la documentation.

5 · ⚠️ Une limite à connaître

Les modules ne fonctionnent pas en double-clic. Ouvrir un fichier directement depuis l'explorateur donne une adresse en file://, et le navigateur bloque les import pour des raisons de sécurité : 

CORS policy: Cross origin requests are only supported for
protocol schemes: http, https…

Il faut un petit serveur local — l'extension Live Preview de VSCode en lance un toute seule.

C'est précisément pourquoi les projets 1 à 8 s'en passent : tout ce que vous avez écrit jusqu'ici fonctionne au double-clic. Cette contrainte n'apparaîtra qu'au projet 12.

6 · Et après ?

Découper son code mène naturellement à une autre question : et si quelqu'un avait déjà écrit ce dont j'ai besoin ? C'est ce que sont les bibliothèques — et la façon de les installer s'appelle npm.

Vous verrez tout cela en fin de journée 3, en démonstration également : jQuery comparé au JavaScript natif, puis npm et le dossier node_modules.
