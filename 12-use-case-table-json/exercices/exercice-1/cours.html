Projet 12 · Cas pratique

Le registre des emprunts

  • 📖 Cours
  • 📋 Énoncé
  • ✍️ À vous de jouer
  • ✅ Solution

Ce que vous allez faire ici : le projet le plus complet du parcours — un tableau piloté par des données, un formulaire qui l'alimente, et un statut calculé pour chaque ligne.

Aucune notion nouvelle, sauf pour le bonus (fetch). Ce cours est une carte : il vous dit où retrouver chaque geste.

1 · Un tableau HTML, ce sont des lignes et des cellules

Le tableau de la page est déjà écrit — sauf son contenu. Sa structure vient du projet 2 : 

<table>
  <thead>
    <tr><th>Livre</th><th>Lecteur</th> … </tr>   ← l'en-tête, fourni
  </thead>
  <tbody>
                                              ← VIDE : votre code le remplit
  </tbody>
</table>
BaliseRôle
<tr>une ligne
<td>une cellule de données
<th>une cellule d'en-tête (déjà écrite)

Rien de neuf côté JavaScript : un <tr> se fabrique avec createElement et s'insère avec append, exactement comme les <li> du projet 9. Seuls les noms de balises changent.

On insère les lignes dans le <tbody>, pas dans le <table> : document.querySelector("tbody").

Visuellement, les deux marchent — et c'est bien le piège. Mais un <tr> ajouté sur le <table> n'entre pas dans le <tbody> : celui-ci reste vide. Votre vidage corps.querySelectorAll("tr") n'efface alors plus rien, les lignes se dupliquent à chaque redessin, et corps.children.length reste bloqué à 0 dans la console.

2 · Une ligne = quatre cellules

const tr = document.createElement("tr");

const tdLivre = document.createElement("td");
tdLivre.textContent = emprunt.livre;

// … trois autres cellules …

tr.append(tdLivre, tdLecteur, tdJours, tdStatut);
corps.append(tr);

C'est la construction imbriquée du projet 9, exercice 3. On fabrique de l'intérieur vers l'extérieur, on n'insère qu'à la fin. Quatre cellules au lieu de deux <span> : même geste, répété.

3 · Une donnée qui n'est pas dans les données

Le statut n'existe nulle part dans le tableau de départ. Il se déduit des jours restants : 

jours < 0    → « En retard »    rouge
jours ≤ 7    → « Bientôt dû »   orange
sinon        → « En cours »     vert

Une fonction qui rend le couple texte + classe :

function statutDe(jours) {
  if (jours < 0)  return { texte: "En retard",  classe: "statut--retard" };
  if (jours <= 7) return { texte: "Bientôt dû", classe: "statut--bientot" };
  return { texte: "En cours", classe: "statut--ok" };
}

Une fonction qui rend un objet — le return du projet 7 et l'objet du projet 8, assemblés. Elle regroupe en un seul endroit toute la règle métier : si les seuils changent, une seule ligne change.

Les trois return s'excluent : dès que l'un s'exécute, la fonction s'arrête. Pas besoin de else.

Attention aux frontières. Elles se testent, et elles se trompent facilement : 

jours = -1   → En retard
jours =  0   → Bientôt dû     ⚠️ zéro n'est PAS négatif
jours =  7   → Bientôt dû     ⚠️ le 7 est inclus (≤)
jours =  8   → En cours

4 · Tout redessiner, jamais retoucher

À chaque changement, on vide le tableau et on le reconstruit entièrement depuis les données. C'est le schéma du projet 9, exercice 4 : 

function afficher() {
  for (const ancienne of corps.querySelectorAll("tr")) {
    ancienne.remove();
  }
  for (const emprunt of emprunts) {
    ajouterLigne(emprunt);
  }
  // … puis le résumé
}

Pourquoi ne pas simplement ajouter la nouvelle ligne ? Parce que le résumé, les statuts et l'ordre dépendent de l'ensemble des données. Tout redessiner garantit que l'affichage ne peut pas diverger des données — au prix de quelques éléments recréés.

Les données sont la vérité, la page n'en est que le reflet. C'est l'idée que vous retrouverez dans tous les frameworks modernes.

5 · Le formulaire ajoute aux données, pas au tableau

emprunts.push({ livre: livre, lecteur: lecteur, jours: jours });
afficher();                                  ← et le tableau suit

L'ordre compte. On modifie d'abord les données, puis on redessine. Insérer directement un <tr> dans la page sans toucher au tableau emprunts marcherait… jusqu'au prochain afficher(), qui ferait disparaître la ligne.

Le reste est le projet 10, exercice 3, à l'identique : 

form.addEventListener("submit", function (evenement) {
  evenement.preventDefault();
  const livre = champL.value.trim();
  // … vérifier, puis push, puis afficher
});

6 · Vérifier une saisie numérique

Les deux premiers champs sont du texte : .trim() puis comparaison à "" suffit (projet 10, exercice 3). Le troisième est un nombre : 

const jours = Number(champJ.value.trim());

if (isNaN(jours)) { … }        ← ce n'est pas un nombre

Number() vient du projet 6, isNaN du projet 7, exercice 4 — souvenez-vous : NaN n'est égal à rien, pas même à lui-même. C'est pourquoi on le teste avec isNaN et non avec ===.

Le champ type="number" filtre déjà beaucoup. Taper « abc » dedans ne produit pas "abc" : le navigateur rend une chaîne vide. Votre test isNaN ne se déclenchera donc quasiment jamais depuis l'interface — il protège contre un collage ou un champ modifié.

Gardez-le quand même. Une vérification qui ne sert jamais coûte deux lignes ; une vérification manquante coûte un bug.

7 · 🎁 Bonus — aller chercher des données ailleurs

Jusqu'ici, vos données étaient écrites dans votre fichier. Elles peuvent venir d'un serveur : 

fetch("https://dummyjson.com/users?limit=5")
  .then(function (reponse) { return reponse.json(); })
  .then(function (donnees) {
    // donnees.users est un tableau d'utilisateurs
  });

Deux étapes, deux .then : la première réponse n'est pas encore les données — c'est une enveloppe, qu'il faut ouvrir avec .json(). Chaque .then dit « quand ce sera prêt, fais ceci ».

C'est le même principe qu'un écouteur d'événement : du code qui ne s'exécute pas maintenant, mais plus tard. Vous connaissez déjà l'idée depuis le projet 10.

fetch ne fonctionne pas en double-clic. Ouverte depuis un fichier (file://), la page se voit refuser la requête. Il faut un serveur local : 

python3 -m http.server 8000

Puis ouvrez http://localhost:8000. C'est le seul moment du parcours où un serveur est nécessaire.

Les données d'une API ne sont jamais à votre format. dummyjson rend des utilisateurs avec firstName, lastName, email — pas des emprunts. À vous de les traduire vers { livre, lecteur, jours }. Ce travail de traduction est l'essentiel du métier quand on consomme une API.
